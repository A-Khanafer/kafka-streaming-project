# Kafka Learning Project

This repository is a personal learning project focused on understanding Apache Kafka by building a distributed event-streaming system with Python.

The goal is not only to make the system work, but to understand what I am building, why each component exists, how Kafka behaves as a distributed system, and how the architecture evolves over time.

Rather than building a complicated system immediately, the project starts with the smallest possible producer → Kafka → consumer pipeline and gradually introduces new concepts as I learn them.

## Project Vision

The long-term goal is to build a realistic distributed network-monitoring platform where Kafka is used to transport events generated by network devices, simulators, or collectors.

Instead of only sending test strings, the system will eventually process network telemetry and operational events such as:

* Interface status changes
* BGP session changes
* Packet and byte rates
* Interface errors and drops
* CPU and memory usage
* Device reachability
* Configuration changes

These events will be published to Kafka and consumed by independent services responsible for different tasks.

The architecture may eventually evolve toward something similar to:

```text
Network Devices / Simulators
            |
            v
    Python Producer
            |
            v
          Kafka
            |
    +-------+-------+-------+-------+
    |               |       |       |
    v               v       v       v
 State           Audit    Alert     ML
Consumer        Consumer  Consumer Consumer
                                    |
                                    v
                           Anomaly Detection
                                    |
                                    v
                         network-anomalies
                              Kafka Topic
                                    |
                                    v
                           Alert / Analysis
```

This allows the project to explore both event-driven architecture and distributed-system concepts using a practical networking use case.

## Machine Learning Goal

A second objective is to eventually build a machine-learning anomaly-detection service that complements the Kafka system.

The ML component will consume historical and real-time network telemetry from Kafka, transform the events into useful features, and detect behavior that differs from normal network activity.

Initial models may include:

* Isolation Forest
* K-Means
* DBSCAN
* One-Class SVM
* PCA for visualization

More advanced techniques can be explored later if there is a reason to introduce them.

Training and inference will remain separate.

A simplified ML flow could eventually look like:

```text
Kafka
  |
  v
ML Consumer
  |
  v
Feature Engineering
  |
  v
Anomaly Detection Model
  |
  v
Detected Anomaly
  |
  v
Kafka Topic: network-anomalies
```

The purpose is not simply to add machine learning to the project, but to understand how an ML service can participate in a real event-driven system.

## Current Architecture

The initial architecture is intentionally simple:

```text
Python Producer
      |
      v
Kafka Broker
      |
      v
Kafka Topic
      |
      v
Python Consumer
```

The producer sends events to Kafka.

Kafka stores those events inside topics.

The consumer reads and processes those events.

At the beginning, these events may simply be test messages used to understand how Kafka behaves.

As the project progresses, they will evolve into structured network events and telemetry.

More components, partitions, consumers, services, and failure scenarios will only be introduced when there is a reason to introduce them.

## Learning Logs

The `learning_logs/` directory is a development and learning journal for the project.

Each learning log documents two things:

1. **What I worked on**
2. **What I understood from it**

Instead of only keeping the final code, I document the steps I took to build the system, the commands I used, the architecture at that point in time, and my current understanding of the concepts involved.

For example, a learning log may explain:

* How I configured Kafka with Docker
* Why Kafka is using different ports
* How I created a topic
* What a topic represents
* What partitions are
* How offsets identify events
* How a producer sends events
* How a consumer reads events
* How consumer groups work
* Problems I encountered and how I solved them
* How my understanding changed after testing something

The logs are written in my own words and reflect my understanding at that stage of the project.

> **Note:** *Learning logs are never AI-generated. They are written entirely by me, by hand, in my own words, based on what I learned from videos, documentation, experimentation, and questions I asked AI while working through the project.*

They are not meant to be formal Kafka documentation.

They are meant to show the progression of the project and how my understanding develops while I build it.

A log might include diagrams, commands, notes, explanations, and examples such as:

```text
Producer
    |
    | localhost:9092
    v
Kafka Broker
    |
    v
network-events
```

or notes explaining a concept such as:

```text
A partition is an ordered append-only sequence of events.

Each partition has its own offsets:

Partition 0

Offset:     0    1    2
Events:    e1   e2   e3
```

This means the learning logs act as both:

* A record of how the project was built
* A record of what I learned while building it

An example structure could be:

```text
learning-logs/
├── day-01.md
├── day-02.md
├── day-03.md
├── day-04.md
├── day-05.md
└── ...
```

> **Note:** *Git steps and commands used throughout the project will also be documented in the learning logs.*

## Learning Approach

The project follows a simple approach:

> Build something, understand why it works, experiment with it, break it, understand what happened, document what I did and what I learned, then move to the next concept.

The system starts intentionally small.

Complexity will only be added when there is a clear reason for it.

The final objective is not simply to have a Kafka application that works. It is to build a realistic distributed network-monitoring platform while developing a deeper understanding of Python, Kafka, event-driven architecture, distributed systems, networking telemetry, and machine learning.
